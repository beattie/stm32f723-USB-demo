# STM32F723 USB Passthrough — Project Overview

## Primary Goal

Learn Embedded Rust through a worked example that produces a genuinely useful device.

The project progresses in two phases:

1. **Hardware bring-up in C** — bare-metal C firmware written with Claude Code to
   accelerate validation of a custom PCB (v0.1). The goal is to confirm all
   peripherals work before investing in the Rust port. Clock, GPIO, USB, SD card,
   and USB passthrough are each verified in C first.

2. **Production firmware in Rust/Embassy** — once hardware is validated, the firmware
   is re-written in Rust using the Embassy async embedded framework. The C bring-up
   code is discarded; the Rust firmware is the deliverable.

The C bring-up code is intentionally minimal and mostly generated by Claude Code.
It is not meant to be maintained or extended beyond bring-up purposes.

---

## The Device

A **USB keyboard interposer with integrated hardware password manager**.

```
[Physical Keyboard]
        |
    USB-A (OTG_FS host, PA11/PA12)
        |
   [STM32F723VETx]  ←→  [MicroSD: credential store]
        |
    USB-C (OTG_HS device, PB14/PB15)
        |
   [Host Computer]
   (sees a standard HID keyboard — no drivers required)
```

Normal keystrokes pass through transparently. A hotkey triggers the device to
inject stored credentials (username + password) as if typed by the keyboard.

Works with any OS, any application, any login prompt — no host software or
drivers required.

See [design.md](design.md) for the full device design.

## Development Approach

### Why C for bring-up?

- Faster iteration: no Cargo/build complexity, direct register access, easy to flash
- Claude Code generates the register-level C quickly, freeing focus for hardware debug
- The C code serves as a translation reference when writing the Rust port
- Rust ownership and lifetime rules are easier to apply once the hardware behaviour
  is understood

### Why Rust/Embassy for production?

- Primary learning goal
- Embassy's async model maps cleanly to the concurrent USB host + device + SD tasks
- Memory safety eliminates a class of bugs that are hard to catch in bare-metal C
- `no_std` + `no_alloc` discipline forces correct reasoning about memory on 256KB SRAM

### Why Embassy specifically?

The STM32F746-DISC reference firmware uses Embassy and the async task model fits
the device architecture well:
- `keyboard_poll_task`: polls USB host, runs state machine, injects credentials
- `usb_device_task`: drives USB HID device (appears as keyboard to computer)
- `sd_task`: manages SD card access

## Related Projects

**Pastilda** ([crowdsupply.com/third-pin/pastilda](https://www.crowdsupply.com/third-pin/pastilda)):
The original inspiration for the USB interposer concept. An open-source USB HID
passthrough password manager — physical keyboard plugs into the device, which
forwards keystrokes to the host and can inject credentials on demand. This project
follows the same fundamental architecture. Hardware has been discontinued and
documentation is becoming scarce. A Bitbucket repo (possibly newer) appears to be
gone. Fork preserved at [github.com/beattie/pastilda](https://github.com/beattie/pastilda).

**stm32f746-disc** (`~/projects/stm32f746-disc`): Rust/Embassy proof-of-concept on
the STM32F746G-DISCO development board. USB passthrough and password manager logic
is implemented here. The STM32F723 firmware is a port of this work to the custom
board.

**ZeroKeyUSB** ([crowdsupply.com](https://www.crowdsupply.com/depbit/zerokeyusb)):
Similar commercial device — offline password manager + Bitcoin hardware wallet.
Uses AES-128, Microchip ATECC secure element, USB HID output. Plans MIT open source
release post-campaign. Worth monitoring for design reference, particularly the
Bitcoin signing implementation (potential model for Monero signing extension).

## Future Extensions (post bring-up)

These are ideas to explore after the core device works, as additional chapters in
the Rust learning worked example:

- **Monero hardware wallet**: store seed/keys on device, offline transaction signing.
  Ed25519 signing is feasible on Cortex-M7. Full RingCT/Bulletproofs is a stretch.
  Monero node runs on `eris`. Architecture mirrors ZeroKeyUSB Bitcoin model.
- **TOTP**: needs RTC or USB time sync
- **FIDO2 / WebAuthn**
- **Display support**: scrollable credential list, password entry masking
